# シーン設計案

> **2026-10-16 注記:** 本書は初期の設計案。行動選択UI・本文UI・日次結果は実装済み（`Assets/Scripts/Scene/MainGrand/`）。遷移先Sceneは表示要求から選ばず `MainGameScene` 固定で、`GameSceneRouteTable` は未使用。現行構成は [21_拡張基盤の初回整備.md](21_拡張基盤の初回整備.md) と [29_別端末再開メモ.md](29_別端末再開メモ.md) の「主な入口」を参照。

この文書は、`行動選択フェイズ` と `紙芝居パート` を前提にした Unity のシーン責務案です。

## 結論

今の段階では、**フェイズごとにシーンを分けすぎない** 方が良い。

最初のおすすめはこれです。

- `InitScene`
  - タイトル
  - セーブ選択
  - 設定
- `MainGameScene`
  - 日付進行
  - 行動選択
  - 紙芝居
  - 日次まとめ
- 将来必要なら追加
  - `RaceScene`
  - `SpecialEventScene`

つまり、**入口は `InitScene` に固定し、行動選択フェイズと紙芝居パートは最初は同じ MainGameScene 内で状態切り替えする** のが一番安全です。

## 現在の採用方針

現時点では、入口は **`InitScene` の Start メニューから入る導線を正式採用** する。

- `InitScene -> Start`
- `GameFlowManager.StartNewGameFlow()`
- 最初の `GameSceneRequest` を見て本編 Scene へ遷移

この段階では、

- `MainGameScene` 直開きは正式導線ではない
- デバッグ導線より本番導線を優先する

で進める。

## なぜ分けすぎない方がいいか

今のゲームの核は、

- 日付
- 時間帯
- スケジュール
- イベント解決
- 報酬反映

です。

ここでシーンを細かく分けると、

- 毎回の状態引き継ぎが増える
- デバッグが難しくなる
- UI と進行ロジックの責務が散る
- まだ固まっていない段階で作り直しコストが増える

ので、今は得より損が大きいです。

## 推奨する責務分け

## 1. InitScene

役割:

- タイトル表示
- New Game / Load / Config / Exit
- セッション初期化の入口

ここでやること:

- `GameSession.IsNewGame`
- `CurrentSaveSlot`
- `GameSession.InitConfig()`

ここでやらないこと:

- 本編の日付進行
- イベント解決
- ADV 表示本体

## 2. MainGameScene

役割:

- 本編のメインループ
- 行動選択フェイズ
- 紙芝居イベント
- 夜のまとめ

ここでは**論理フェイズの切り替え**を中心に運用する。

ただし進行状態そのものは Scene 内に持たず、
`GameFlowManager` が永続保持する。

想定フェイズ:

- `ResolveSchedule`
- `ActionSelection`
- `Novel`
- `MiniGameAction`
- `DailySummary`
- `AdvanceTime`

## 3. RaceScene

これは最初は不要。

後から以下のどちらかで判断する。

- レースがテキスト寄りの簡易解決なら `MainGameScene` に残す
- レースが専用 UI、専用演出、専用カメラを持つなら `RaceScene` に分離する

## 4. SpecialEventScene

これも最初は不要。

ただし以下の条件が揃ったら分ける価値がある。

- 専用背景や演出が大量に必要
- 通常日課と UI 構造が大きく異なる
- 読み込みコストを分離したい

## MainGameScene 内の状態設計

`MainGameScene` は 1 シーンのまま、**`GameFlowManager` から来る Scene 要求を処理する受け口** として使う。

例えば:

```csharp
public enum GameFlowPhase
{
    None,
    ResolveSchedule,
    ActionSelection,
    Novel,
    MiniGameAction,
    DailySummary,
    AdvanceTime,
    Finished,
}
```

## 現在の実装状況

実装済み:

- `InitScene` の Start から `GameFlowManager.StartNewGameFlow()` を呼ぶ
- `GameFlowManager` が現在フェイズと現在イベントを保持する
- `GameSceneRequest` / `GameSceneResult` で Scene 間の受け渡し型を定義した
- `MainGameScene` は `GameFlowManager` の要求を処理する側へ寄せ始めている
- 現時点では論理シーンはすべて一旦 `MainGameScene` に向けている

未実装:

- 実際の `ActionSelection` UI
- 実際のノベル再生 UI
- 実際のミニゲーム Scene
- `SceneRequest -> 表示 -> ユーザー入力 -> SceneResult` の本実装

## MainGameScene 内の表示レイヤー

Scene を増やす代わりに、表示レイヤーを分ける。

- `BaseHUD`
  - 日付
  - ステータス
  - 所持金
- `ActionPanel`
  - 行動選択
- `ScenarioPanel`
  - 会話表示
  - 立ち絵
  - 名前欄
- `SummaryPanel`
  - 1 日の結果
- `DebugPanel`
  - 現在フェイズ
  - 現在イベント

このやり方なら、**紙芝居パートは別シーンではなく、ScenarioPanel を前面に出すだけ** で済む。

## 紙芝居パートを別シーンにしない理由

紙芝居イベントは本質的には、

- ある日付
- ある時間帯
- あるイベントID

に紐づいた本編進行です。

別シーンにすると、

- 今どの日付か
- どのイベント報酬を反映したか
- どこへ戻るか

を毎回持ち回る必要があり、今の段階だと過剰です。

なので、**ADV 表示は MainGameScene 内の 1 パネルとして扱う** のが良いです。

## フェイズ遷移の基本形

```text
InitScene
  Start
    -> GameFlowManager.StartNewGameFlow()
    -> ResolveSchedule
    -> ActionSelection or Novel
    -> MiniGameAction (必要時)
    -> DailySummary (必要時)
    -> AdvanceTime
    -> ResolveSchedule
```

## 将来分けるべき境界

以下の境界は後で分けやすいようにしておく価値がある。

- 進行制御
- 画面表示
- シナリオ再生
- レース再生

つまり、**コードの責務は分けるが、Scene はまだ増やさない** のがポイント。

## 今の開発段階でのおすすめ

### 今やる

- `InitScene` 起点を正式導線として固定する
- `MainGameScene` 1つで論理フェイズを受ける
- `GameFlowManager` を中心に進行を持つ
- デバッグ表示で現在フェイズと現在要求を見えるようにする

### まだやらない

- 行動選択用 Scene
- ADV 専用 Scene
- まとめ画面専用 Scene

## 実装イメージ

### Presenter

- MainGame 全体のフェイズ制御

### Model / Service

- スケジュール解決
- イベント解決
- 時間進行
- 報酬適用

### View

- どのパネルを表示するか
- 選択肢入力
- シナリオ表示

## まとめ

今の正解は、

- シーンは少なく
- フェイズは多く
- 責務はコードで分ける

です。

特にこのゲームでは、`行動選択` と `紙芝居` は**本編の連続した流れ**なので、まずは同一 Scene 内で回す設計が一番相性が良いです。

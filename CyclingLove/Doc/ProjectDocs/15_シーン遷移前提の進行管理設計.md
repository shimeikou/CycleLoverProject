# シーン遷移前提の進行管理設計

この文書は、`行動選択フェイズ -> ノベルフェイズ -> ミニゲームアクションフェイズ` のように、
本編中で Unity の Scene を跨いでも破綻しない進行管理の方針を整理したものです。

## 結論

シーンを跨ぐ前提では、

- `進行状態` は Scene に持たせない
- `Scene は入力と表示に専念` する
- `進行の司令塔` を `DontDestroyOnLoad` な永続マネージャに置く

の3点が必須です。

今回の推奨構成はこれです。

- `InitScene`
  - New Game / Load / Config / Exit の入口
  - `StartNewGameFlow()` の起点
- `GameSession`
  - セーブや現在日付などのセッション状態
- `GameFlowManager`
  - 今どのフェイズか
  - 今どのイベントを処理中か
  - 次にどの論理シーンへ行くか
- 各 Scene Presenter
  - 画面表示
  - ユーザー入力
  - フェイズ完了時に `GameFlowManager` へ結果を返す

## 物理シーンと論理シーンを分ける

大事なのは、`Unity 上の Scene 名` と `ゲーム進行上の Scene 種別` を別物として扱うことです。

例えば論理上はこうです。

- `ActionSelection`
- `Novel`
- `MiniGameAction`
- `Summary`

ただし、開発初期は全部を物理的に `MainGameScene` へ載せてもよいです。

つまり今は、

- 論理シーンは分ける
- 物理シーンはまだ分けない
- 入口だけは `InitScene` に固定する

という段階にできます。

後から `NovelScene` や `MiniGameScene` を作っても、
ルーティングテーブルの差し替えだけで移行しやすくなります。

## 推奨ループ

基本ループは以下です。

```text
ResolveSchedule
  -> ActionSelection
  -> Novel
  -> MiniGameAction (必要なときだけ)
  -> DailySummary (必要なときだけ)
  -> AdvanceTime
  -> ResolveSchedule
```

## なぜ Scene 側に状態を持たせないか

Scene を跨ぐと、

- `MonoBehaviour` は破棄される
- Inspector 参照は切り替わる
- 一時変数は消える

ので、`MainSceneModel` のような Scene ローカルな進行保持だけでは最終形に弱いです。

特に壊れやすいのは、

- 今どのイベントの途中か
- ノベル終了後に何へ戻るか
- ミニゲーム結果をどこへ反映するか
- 日付進行をいつ確定するか

です。

## GameFlowManager の責務

`GameFlowManager` には以下を持たせます。

- 現在フェイズ
- 現在イベント
- 現在の Scene 要求
- Scene 完了結果の受け取り
- 次フェイズの決定
- 日付進行の確定

今回追加した型:

- `GameFlowPhase`
- `GameFlowSceneType`
- `GameSceneRequest`
- `GameSceneResult`
- `GameSceneRouteTable`
- `GameFlowManager`

## 現在の実装反映

現時点でコードに反映済みの項目:

- `InitScene` の Start から `GameFlowManager.StartNewGameFlow()` を呼ぶ
- `GameFlowManager` が `CurrentPhase` / `CurrentEvent` / `CurrentRequest` を保持する
- `GameSceneRequest` と `GameSceneResult` を定義した
- `LastEventApplicationResult` を保持して、報酬ログを Scene 側で参照できる
- `MainGameScene` は `GameFlowManager` の返す要求を順に処理する方向へ変更した

まだ仮実装の項目:

- `ActionSelection` は自動選択
- `Novel` は自動完了
- `MiniGameAction` はプレースホルダ
- `Summary` はプレースホルダ
- 論理シーンはすべて一旦 `MainGameScene` に割り当て

## Scene の責務

各 Scene は以下だけやればよいです。

### ActionSelection Scene

- 候補アクションを表示
- 選択結果を `GameSceneResult.SelectedActionId` に詰める
- `GameFlowManager.SubmitSceneResult(...)` を呼ぶ

### Novel Scene

- `ScenarioId` を使って紙芝居を再生
- 終わったら `NovelClosed` を返す

### MiniGameAction Scene

- アクションやレースを実行
- スコアや成功失敗を返す

### Summary Scene

- その時間帯や一日の締めを表示
- 閉じたら `SummaryClosed` を返す

## 今回のコード方針

現時点ではまだ専用 Scene を増やしていないので、
`GameSceneRouteTable` は各論理シーンを一旦すべて `MainGameScene` に向けています。

これにより、

- まずは1 Scene でデバッグできる
- 後で物理 Scene を分けても進行ルールは流用できる

という移行しやすい形になります。

## 次にやるべき実装

優先順はこれです。

1. `MainGameScene` を `ActionSelection / Novel / Summary` 表示切り替え対応にする
2. `GameFlowManager` を使って `SceneRequest -> 表示 -> SceneResult` の本実装へ置き換える
3. `ActionSelection` の自動選択を UI 入力へ差し替える
4. `Novel` の自動完了をシナリオ再生へ差し替える
5. `NovelScene` と `MiniGameScene` を後から必要に応じて実体化する

## 補足

この設計のポイントは、

- 今は1 Scene でも開発を進められる
- 最終的に複数 Scene へ割っても進行が崩れない

ことです。

つまり、`Scene を増やすかどうか` と `進行設計の強さ` を切り離しておくのが狙いです。

# 開発の進め方

この文書は、今の Unity プロジェクトを破綻させずに、段階的にゲームとして成立させていくための進め方をまとめたものです。

## 基本方針

- 一気に全機能を作らない
- まずは 1 本の細いプレイ体験を最後まで通す
- データ仕様を先に決め、画面や演出は後から厚くする
- UI より先に進行ロジックを安定させる

## おすすめの進め方

### 1. 企画用語を固定する

先に固定したいもの:

- ステータス名称
- 時間帯名称
- ルート解放条件の呼び方
- 機材カテゴリ名
- イベント種別名

これを先に決める理由:

- コード、ScriptableObject、UI 文言のズレを防ぎやすい

### 2. 最小ループを先に完成させる

最初に成立させたいプレイ体験:

1. タイトル開始
2. 初回導入イベント
3. 午後行動を選ぶ
4. 夜に結果確認
5. 翌日に進む
6. 数日後にヒロインイベントが起きる

この段階では不要なもの:

- 全ヒロイン
- 本格レース
- 全ブランド
- 高度な UI 演出

### 3. 1 ルートで縦切り検証する

最初の 1 ルートで確認したいこと:

- 会話イベントが気持ちよく読めるか
- ステータス条件が分かりやすいか
- 行動選択に意味があるか
- 1 週間から 1 か月分の進行が退屈でないか

### 4. データ主導に寄せる

できるだけコードにハードコードしない方が良い項目:

- 日付ごとのイベント
- 好感度条件
- ステータス条件
- 購入価格
- パーツ性能
- レース難度

メリット:

- 後から調整しやすい
- シナリオ追加が楽になる
- バランス調整のコストが下がる

## 実装のレイヤー分け

### レイヤー 1 コアモデル

- 日付
- プレイヤー状態
- バイク状態
- 好感度
- 資金

### レイヤー 2 進行制御

- イベント引き当て
- 時間進行
- 条件判定
- 分岐管理

### レイヤー 3 表示

- UI 表示
- シナリオ表示
- ステータス表示
- 選択肢表示

### レイヤー 4 コンテンツ

- ヒロインイベント
- 地域イベント
- ショップ
- レース

## 開発サイクル

おすすめの 1 サイクル:

1. 小さな仕様を 1 つ決める
2. データ構造を決める
3. 最小実装を入れる
4. ダミーデータで動かす
5. UI に出す
6. 触って違和感を直す

## 実装時の注意

### スケジュール依存を強くしすぎない

- 全イベントを日付固定にすると運用が重くなる
- 条件型イベントと日付固定イベントを分けると扱いやすい

### ルート分岐を早く複雑にしすぎない

- 最初は排他ルートにしすぎない
- 序盤は複数ヒロインと自然に関われる方が検証しやすい

### レースを重くしすぎない

- まずは簡易シミュレーションで良い
- 面白さの核がシナリオなら、先にそちらを成立させる

## 直近 2 週間の進め方案

### 1 週目

- 用語統一
- `GamePlayerData` の整理
- 進行管理の整理
- イベント再生の最小化
- 3 日から 7 日のダミーデータ作成

### 2 週目

- ヒロイン 1 名の導入から進展まで実装
- 好感度と条件分岐
- 行動 UI
- セーブロードの実地確認

## 実装担当が 1 人でも回しやすい順番

- 仕様確定
- データ構造定義
- ダミーデータ作成
- ロジック実装
- UI 接続
- シナリオ投入
- 調整

## 次にやると効果が高いこと

1. `GamePlayerData` の正式項目を決める
2. `GameEventType` を整理する
3. `ScheduleDay` の完成形を決める
4. 自由行動イベントのデータ形式を決める
5. サンプル 1 週間をデータで作る

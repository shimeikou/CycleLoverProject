# 年間進行基盤仕様

更新日: 2026-10-16

## 目的

T21の最初の実装として、現行10日版を変更せず、1年間の日付・四季・休日・特別枠・季節目標・年末結末を外部データから解決する基盤を追加する。ヒロイン固有イベント、年間バランス、スキップ仕様は後続のT21〜T24で接続する。

## 正本データ

`Assets/Resources/Content/AnnualCalendar.json` を編集用の正本とする。初期定義は2026年4月1日から2027年3月31日までで、春・夏・秋・冬が全日を重複なく覆う。

- `WeekendsAreHolidays`: 土日を休日として扱う。
- `DateOverrides`: 日付単位で休日／平日を上書きし、特別枠IDを0件以上指定する。
- `SeasonGoals`: 季節、締切、条件、成功／未達フラグを定義する。
- `Endings`: 優先度順に条件を評価する。条件なしの未達結末を必須のフォールバックとする。

日本の祝日、季節目標の数値、告白相手の確定条件は企画上の未確定事項なのでコードへ固定しない。現在の `goal_*_ready` と `annual_confession_ready` は、後続ルートが達成時に付与する統合用フラグであり、最終バランス値ではない。

## 検証規則

- 開始日から終了日までがちょうど1年間である。
- 四季は4件で、各日が必ず1つの季節だけに属する。
- 日付例外は期間内かつ重複なし。休日指定は `inherit / holiday / workday` のいずれか。
- 季節目標の締切は対象季節の範囲内に置く。
- 結末IDと優先度は重複不可。条件なしの結末を最低1件置く。
- ビルド前のコンテンツ検証で年間JSONも読み込み、異常時はビルドを中止する。

## 現在の実装範囲

`AnnualCalendarService` は任意の日付について曜日、季節、休日、特別枠、最終日を返す。季節目標は既存の `CampaignCondition` で判定し、成功／未達フラグを返す。年末結末は優先度順に条件を評価する。

`AnnualProgressService` は締切日以降の季節目標と最終日の年末結末をプレイヤー状態へ一度だけ適用する。結果ID、成否、結果フラグ、判定日を保存し、同じ処理を再実行してもフラグとRevisionを重複更新しない。保存形式はv3とし、v1／v2から不足欄を補完する。年間結末は未確定状態を明示して途中保存と区別する。

`CampaignGameService` は年間定義を任意依存として受け取り、各 `GameSceneRequest` へ季節ID・表示名、休日、最終日、特別枠IDを載せる。画面側（`Scene/MainGrand`）はまだこれらを表示していない。日次結果を閉じる際は日付を進める前に期限到達済みの未確定目標を補完し、最終日には年末結末も確定する。現行10日版も同じ接続を使うため、年間版への切替で進行コードを分岐させない。

`AnnualCampaign.json` と `AnnualSchedule.json` は年間版の候補データ。日程側には平日・休日・季節締切・年末のテンプレートだけを置き、カレンダーの日付、休日、季節、特別枠と優先ルールから起動時に365件の一意な `CampaignDay` を生成する。365日の展開はカレンダーの `StartDate` から、進行の開始日は `AnnualCampaign.json` の `StartYear`／`StartMonth`／`StartDay` から取る。両者の一致は検査していないため、開始日を変えるときは両方を揃える。また実行時に渡すカレンダーは `CalendarResource` ではなく固定キー `Content/AnnualCalendar`（`GameFlowManager.cs`）。現在のプレイヤー向け実行対象は10日版のままにし、年間候補はビルド前検証で構造と参照を確認する。

2026-10-16時点で、1年間・四季・週末と最終日特別枠、季節目標の成功／未達、年末結末の優先度とフォールバック、結果の一度だけの適用とJSON復元、6月30日の日次進行からの自動確定、薄い日程からの365日展開をEditModeテストで確認。全体で59ケース成功、コンパイル失敗なし。
